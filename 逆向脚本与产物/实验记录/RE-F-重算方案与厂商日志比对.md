> 目标：把「一加13 解容模块需要原厂终止电压」所用的重算方案
> （`06-修复候选-uv_dt_orig-v12/log_v12.sh` 的 `uv_dt_orig()`）
>
> ⚠️ **[2026-10-05 溯源说明]** 该候选目录**已删除**（修复早已并入主线，且其中的 `log_v12.sh` 是比主线更旧的变体，
> 长期造成误导）。本文提到的"推 `log_v12.sh` 到真机"现在就等价于推 **`模块源目录/log.sh`**（主线）。

### 1.4 被验证的算法（= v12 实现）

```
ratio   = 10 × deep_dischg_counts / cc            （整数除；仅 0 < cc < 5000）
region  = ratio 与 [20,30,50,70,90] 升序比较，≥ 即抬档   → 0=min 1=low 2=mid_low 3=mid 4=mid_high 5=high
index_t = 温度与 [-50,100,350] 升序比较，≤ 归下档       → 0=cold 1=cool 2=normal 3=warm
row k   = max{ i : max(0, row[i].f0 − count_cali) ≤ cc }  （含等号；无满足取第 0 行）
输出    = row[k].vbat1
```

### 3.2 温度档未知的 112 条是怎么判的

这些记录（`ddrc_status`）本身不带温度。做法：
对 index_t ∈ {cold,cool,normal,warm} 各算一遍，若**日志值落在候选集合内**即记为"一致（值域判定）"，
并记录命中的档位。逐条候选集合与命中档位已写入 CSV 的 `温度档未知时的候选值`/`候选命中档` 列。

- 109 条命中；其中大多数只被 **normal/warm** 两档命中（因为这两档多数格子相同），
  少数被单档唯一命中（例如 counts=1758/cc=344 必须 normal 或 warm；counts=1699/cc=335 亦然）。
- 3 条不命中 —— 即 §5.1 的 2800 改表样本。

> 这不是"放宽判据"：因为**行选择 k 只由 cc 决定**，与温度无关；温度只决定用哪张 4 行/6 行的表。
> 对同一 region，四档表的 vbat1 序列在高 cc 段大量重合，因此 109 条里绝大多数其实是**强判定**。

### 3.3 与"表"无关的逻辑层检验（这部分对所有样本都成立）

| 检验 | 结果 |
|---|---|
| `ratio == ⌊10·counts/cc⌋`（日志自带 ratio 字段） | **136 / 136** |
| 日志 `ratio_p` == 规则算出的 region（≥ 抬档） | **22 / 22** |
| 日志 `index`（驱动自报的行号 k） == 规则算出的 k | **22 / 22** |
| 日志 `temp_p` == 由 `tbat` 按 ≤ 归下档推出的 index_t | **21 / 22**（唯一例外见 §5.2） |
| 日志 `count_thr` == 选中行的 `f0` | 18 / 24（6 条例外见 §5.3） |

> 也就是说：**驱动的"选表 + 选行"两维逻辑，被日志自身打印的 `ratio_p` / `temp_p` / `index` 三个字段
> 独立复核通过**，不依赖任何电压数值。

### 3.4 count_cali（v12 里的 `− count_cali` 项）在语料里**不可检验**

- 语料中 `count_cali` **全部为 0**（crux 字段直读）。
- 真机 `/sys/devices/virtual/oplus_chg/common/deep_dischg_count_cali` 也 = **0**。
- 敏感性：把该项去掉重算，"pred(减 cali) != pred(不减 cali)" 的记录数 **0 / 24**。
- ⇒ 该项在本语料中**不影响任何结果**，既没被证伪也没被证实。
  它的正确性仍只依赖 RE-B §12 的代码级证据（`0x18cb70 subs w10,w10,w11`）。
  **风险等级：低**（真机上恒 0），但**"若某 ROM 出现非 0 cali，v12 的行为未经日志验证"**这一条必须写进边界。

## 5. 不一致与异常逐条解释

### 5.1 不一致样本（3 条）：**社区 dtbo 改表期（2800）**

| 样本 | 来源 | 偏移 | counts | cc | ratio | region | 日志 vterm_final | 重算值 | 候选值 |
|---|---|---|---|---|---|---|---|---|---|
| S040 | `BACKUP-20260926/oplusreserve5.img` | 0x15ae43f | 763 | 172 | 44 | 2 | **2800** | 3060 | cold 3000 / cool·normal·warm 3060 |
| S041 | 同上 | 0x15ba522 | 763 | 172 | 44 | 2 | **2800** | 3060 | 同上 |
| S042 | 同上 | 0x15c444d | 763 | 172 | 44 | 2 | **2800** | 3060 | 同上 |

**判定：不是算法错误，而是"当时的表不是原厂表"。** 四条独立证据：

1. **2800 不是原厂表里任何一格的 vbat1**（值集合见 §4）。任何 (region,index_t,k) 组合都算不出 2800
   —— 因此"重算方案"在这条样本上**必然**失配，与实现无关。
2. 这 3 条的四元组是 `[2800, 2800, 2800, 2800]`（**四元素全等**）；而原厂表的四元组第 3/4 元素
   恒比第 1/2 元素低 50~60 mV（如 `[3250,3250,3200,3200]`、`[3060,2800,3000,2740]`）。
   "偏移归零"正是"把曲线数值整段改成 2800"的指纹（RE-D 第三批 §2.4 已建立该判据）。
3. 同刻的 `deep_term_volt=2800`、`update_vbat_uv [2800, 0] -> set uv_thr=2800`，
   以及同窗口唯一带日历时间的 crux `2026-03-27 21:21:14 … vterm_final@@2800` 全部指向 2026-03 的改表窗口。
4. 同一分区里存在**改表窗口之后的原厂对照样本**：
   同 counts=763 的 S015 `cc=173, ratio=44, region=2, temp_p=3, index=1, count_thr=15, vterm_final=3060`
   —— 用同一张原厂表算，**cc=173 → k=1 → row1.vbat1 = 3060 ✅**。
   即"改表期是 2800、还原后立刻回到 3060"，原厂表在 cc=172/173 上的正确答案都是 3060。

⇒ 这 3 条属于任务书所说的「**跨 ROM（跨表）样本，只比对逻辑不比对数值**」类别：
它们的 `ratio == ⌊10·counts/cc⌋` 自洽、region 判定正确，**逻辑部分通过，数值部分不适用**。

### 5.2 温度档边界样本（1 条）：`tbat = 350` 恰好卡在阈值

S015：`tbat@@350`（35.0 °C），日志 `temp_p@@3`（warm），而按 `≤ 归下档` 规则算得 index_t=2（normal）。
- 阈值 `oplus,temp_range[2] = 350`，若按 `b.le`（≤ 归下档）应为 2，实测是 3。
- **对结果无影响**：该样本 region=2(mid_low)，normal 与 warm 两格完全相同（row1=(15,3000,3060,1)），
  两种档位都给 **3060 = 日志值**。
- 解释（二选一，均不影响 v12）：(a) 驱动比较用的是**另一路温度**（voter/NTC 值），它与 `tbat` 相差 ±0.1 °C；
  (b) 边界比较实际是严格小于。**建议**：v12 保持与代码级证据一致的 `≤`，但在文档里注明
  "温度恰好等于 -50/100/350 时档位可能归上不归下，实测值相同、不影响输出"。

### 5.3 `count_thr` 与选中行 f0 不符（6 条）：**日志字段是滞后/默认值，不影响取值**

| 样本 | cc | 日志 count_thr | 规则选中行 f0 | 说明 |
|---|---|---|---|---|
| S044,S045,S129,S133 | 1 | 50 | 0 | 50 = DT `deep_spec,count_thr` 的默认值 |
| S104 | 10 | 50 | 0 | 同上 |
| S017 | 172 | 0 | 15 | 2800 改表期的 β 记录（表已不同于原厂，行首 f0 也可能被改） |

- 前 5 条都出现在 **cc ≤ 10 的"准新机"样本**（counts 0~30，2025-10-26 / 2025-11-05）：
  `count_thr` 还是 DT 默认 50，说明该缓存字段在早期尚未被周期任务刷新。
- **不影响结论**：这 5 条的日志值都是 3060，而规则（cc=1 或 10 → k=0 → row0.vbat1=3060）**完全吻合**。
- 结论：`count_thr` 是**诊断字段**，不能用来反推 k；反推 k 应该用 `index`（α 记录里可用，22/22 正确）。

### 5.4 其他"看起来像不一致"的现象（已排除）

| 现象 | 排除理由 |
|---|---|

1. **`count_cali = 172/310/222/315/344` 是误读。**

## 7. 结论与置信度

### 7.1 结论

1. **当前重算方案（v12 / `uv_dt_orig`）是准确的。**
   在"表与原厂一致"的 ROM 上，134 条原始样本中判定适用的 131 条**全部一致**（100%），
   覆盖 3060 / 3150 / 3250 三个档位、19 组不同的 (counts,cc) 输入、cc 从 1 到 344、counts 从 0 到 1758。
2. **算法的每一段都拿到了独立证据**：
   ratio 公式（136/136）、region 的 "≥ 抬档"（22/22 + ratio=30 边界样本）、
   index_t 的 "≤ 归下档"（21/22，1 条边界）、行选择 k（22/22）、`vbat1` 的字段位置（与 `deep_term_volt` 分流验证）。
3. **唯一失效场景是"表被改写"**（社区 dtbo 解容期把曲线整段改成 2800）。
   这不是方案缺陷：**任何"按厂商表复刻"的方案在该场景都必然给出原厂值而非被改写的值**——
   从解容模块的角度看，这恰恰是期望行为（我们要的是"原厂会是多少"）。
4. **不能从日志验证的部分**：`− count_cali` 项（真机/语料恒 0）、`gauge_type==1(BQ27411)` 时
   cc 被 SOH 覆盖的分支（本机 gauge_type=0，不生效）。

### 7.2 置信度

| 结论 | 置信度 | 依据 |
|---|---|---|
| v12 在"原厂表"ROM 上输出 == 厂商日志 `vterm_final` | **高** | 131/131，19 组输入、3 个档位、跨 4 种驱动构建 |
| region 判定为 "≥ 抬档" | **高** | 22/22 + 唯一边界样本 ratio=30 → ratio_p=2 |
| index_t 判定为 "≤ 归下档" | **中高** | 21/22；唯一例外是 tbat 恰好 =350，且不影响取值 |
| 行选择 `k = max{i: f0 ≤ cc}` | **高** | 22/22（用驱动自报的 `index` 字段交叉验证） |
| `− count_cali` 项 | **低（不可测）** | 语料与真机 cali 恒 0；仅代码级证据 |
| "2800 那 3 条 = 改表期" | **高** | 2800 非原厂表取值 + 四元组全等指纹 + 同窗口日期 + 同 counts 的原厂对照样本 |
| 跨 ROM 数值可比性 | **高** | 4 个 ROM 的 dtb5 表与真机逐字节相同；`15.0.0.126` 表不同但语料中无该族样本 |

### 7.3 适用边界（必须写进模块文档）

1. **表未被改写**时才成立。若用户用社区 dtbo/其它模块改过 `ddrc_strategy`，v12 给的是"原厂值"，
   与当时 IC/表里的值不同 —— 这是设计意图，不是 bug；但要在 README 里写明"本函数回答的是原厂会取什么值"。
2. **`count_cali` 必须可读且为 0**。若某 ROM 出现非 0 cali，v12 会按其公式处理，但**这一分支未经日志验证**。
   建议：v12 在 DEBUG 行里把 cali 打出来（已打），并在 cali≠0 时额外打一条警告。
3. **gauge_type=1（BQ27411）时除数被 SOH 覆盖** —— 未复刻，本机不适用。
4. **温度读失败时回退 warm(3)、ratio 读失败回退 high(5)** —— 照抄厂商，但这两条回退路径在语料中
   **没有对应样本**（因为样本里温度/ratio 都在），只能算"照抄代码级行为"，置信度中。
5. `count_thr` 在极早期（cc ≤ 10）仍是 DT 默认值 50 —— 如果将来有人想用该字段做健康检查，需注意这个滞后。
